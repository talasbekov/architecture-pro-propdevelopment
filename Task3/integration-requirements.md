# Требования к интеграции с платформой умного дома

## 1. Область и границы данных

- Интеграция покрывает домофон и шлагбаум: получение доступных устройств, отправку команды открытия, управление разрешениями и получение результата команды/событий устройства.
- PropDevelopment остаётся источником истины для связи `управляющая компания → дом → помещение → собственник/жилец`, согласий и решений о доступе. Партнёру передаётся только минимум данных, необходимый для конкретной операции.
- Идентификаторы партнёра отделяются от внутренних идентификаторов; таблица соответствий хранится в интеграционном контуре. Партнёр не получает CRM-профиль, платёжные данные и сведения, не связанные с доступом.
- Каждый запрос и запись содержат обязательный tenant scope: управляющая компания, здание/ЖК, помещение или зона доступа и субъект (собственник/жилец). Доступ между tenant запрещён по умолчанию и проверяется сервером, а не значениями из клиента.

## 2. Аутентификация и авторизация

- Пользователь входит через корпоративный IdP по OpenID Connect (OIDC); мобильный клиент использует Authorization Code Flow с PKCE. Короткоживущий access token предназначен для API Gateway и не передаётся партнёру.
- API Gateway валидирует issuer, audience, подпись, срок действия и scopes. Авторизация сочетает роль, tenant scope, принадлежность объекта, тип операции, действующее согласие и срок разрешения (RBAC + атрибутные проверки).
- Межсервисные вызовы внутри PropDevelopment и соединение с партнёром защищаются mTLS. Для machine-to-machine доступа используется OAuth 2.0 Client Credentials с отдельными scopes (`device.read`, `door.open`, `barrier.open`, `access.manage`, `event.publish`).
- Учётные данные партнёра изолированы по средам, хранятся в secrets manager, автоматически ротируются; сертификаты и ключи отзываются без релиза приложений. Совместные учётные записи запрещены.

## 3. Биометрия, номера автомобилей и согласие

- Распознавание лица и номера автомобиля включается только после явного, информированного и отзывного согласия с зафиксированными целью, устройством/зоной, сроком и версией условий. Отзыв должен быстро блокировать дальнейшее использование и инициировать удаление у партнёра.
- PropDevelopment не хранит и не получает сырые изображения лица, видеопоток и биометрические шаблоны. Если будущий сценарий объективно потребует шаблонов, необходимы отдельное обоснование, оценка рисков, правовое согласование и изолированное защищённое хранилище.
- Для номерных знаков предпочтительны токенизированные или односторонне преобразованные значения, если партнёрский протокол позволяет сопоставление без открытого номера. Открытый номер передаётся лишь для создания/обновления разрешения и не попадает в логи.
- Срок хранения согласий, разрешений, кадров/изображений и событий задаётся по цели и договору. По истечении срока данные удаляются либо необратимо обезличиваются; удаление подтверждается партнёром. Резервные копии учитывают тот же жизненный цикл.

## 4. Защита каналов и платформы

- Внешний трафик проходит через API Gateway/WAF по HTTPS с TLS 1.2+ (TLS 1.3 предпочтителен), современными наборами шифров и отключёнными устаревшими протоколами. Связь с партнёром ограничена сетевым allowlist, mTLS и минимально необходимыми исходящими/входящими маршрутами.
- Данные шифруются при передаче и хранении. Ключи управляются через KMS/HSM с разделением обязанностей и регламентом ротации; секреты не хранятся в исходном коде, образах и конфигурационных файлах.
- WAF, rate limit и квоты применяются по пользователю, tenant, устройству и клиенту партнёра. Для команд открытия предусматриваются более строгие лимиты, защита от повторов и сигнализация о переборе.
- Входные данные проверяются по схеме и бизнес-ограничениям: тип/идентификатор устройства, допустимая зона, формат номера, размер, кодировка и временная метка. Неизвестные поля и устройства отклоняются; ответы партнёра также считаются недоверенными.

## 5. Взаимодействие и надёжность

1. Мобильное приложение получает OIDC access token и отправляет команду с `request_id` и `Idempotency-Key` в API Gateway по HTTPS REST.
2. Gateway проверяет токен, rate limit и базовые scopes; tenant-core-app подтверждает принадлежность пользователя к УК/дому/помещению.
3. Smart Home Integration Service запрашивает у Consent & Access Registry действующее согласие и разрешение для конкретного субъекта, устройства, действия и времени. При отсутствии однозначного разрешения действует fail closed.
4. Только после положительного решения сервис создаёт отдельный M2M-токен и отправляет партнёру минимальную команду по HTTPS REST с mTLS. Пользовательский токен и лишние персональные данные наружу не передаются.
5. Партнёр синхронно подтверждает приём, а окончательный результат/статус доставляет подписанным HTTPS callback либо через согласованный асинхронный поток. Интеграционный сервис проверяет mTLS, подпись, timestamp, nonce, request ID и принадлежность устройства, затем дедуплицирует событие.
6. Решение, команда и результат записываются в аудит и коррелируются по request ID; в мобильное приложение возвращается безопасный статус без внутренних деталей.

- Изменяющие операции идемпотентны; повтор с тем же ключом не вызывает второе открытие. Дубликаты и события не по порядку обрабатываются безопасно.
- Для каждого вызова заданы короткие connect/read timeouts. Повторы разрешены только для безопасных или идемпотентных операций, с exponential backoff и jitter; используются circuit breaker и ограниченная очередь. Команда открытия не считается успешной без явного результата.
- Контракт версионируется (`/v1` или negotiated schema version); изменения проходят contract/security testing и период совместимости. Неизвестная версия отклоняется.

## 6. Аудит, наблюдаемость и эксплуатация

- Неизменяемый аудит фиксирует субъект/сервис, tenant, устройство, действие, решение policy/consent, время, request ID, результат и причину отказа. Сырые биометрические данные, открытые номера, токены, секреты и чувствительные payload в аудит и технические логи не записываются.
- Метрики и алерты включают SLA/SLO доступности и задержки, процент ошибок/отказов, таймауты, открытый circuit breaker, отставание событий, дубликаты, неуспешную проверку подписи и аномальные команды открытия. PropDevelopment и партнёр согласуют окна поддержки и эскалацию.
- Трассировка использует технический correlation/request ID без персональных данных. Доступ к логам и аудиту ограничен ролями; сроки хранения и контроль целостности документированы.
- Runbook описывает отказ партнёра, компрометацию ключа, ошибочную выдачу доступа и утечку. Должны быть доступны немедленный отзыв токенов/сертификатов, блокировка tenant/устройства/операции, отзыв согласия, остановка callback и уведомление ответственных сторон.

## 7. Организационные и правовые условия

- До продуктивного запуска выполняются threat modeling, DPIA/оценка воздействия на приватность, тестирование изоляции tenant, security review партнёра и проверка сценариев отзыва/удаления.
- Договор/DPA фиксирует цели и роли сторон при обработке данных, перечень данных и субподрядчиков, регионы обработки, меры защиты, сроки хранения/удаления, право аудита, уведомление об инциденте и помощь при запросах субъектов.
- Правовая служба подтверждает применимые требования и формулировки согласия до запуска. Конкретные нормы не подменяются архитектурными предположениями.
