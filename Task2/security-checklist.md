# Проверочный лист безопасности бизнес-систем PropDevelopment

## Обоснование состава проверочного листа

Раздел **«Управление доступом»** необходим из-за неоднородной модели идентификации. По исходной C4-диаграмме видны несколько компонентов Active Directory, а также отдельные auth-service и auth-db; это подтверждает множественность контуров, но само по себе не описывает их регламенты и интеграцию. При этом партнёрские API не обеспечивают надёжную изоляцию управляющих компаний. Поэтому важно проверить не только наличие аутентификации, но и единый жизненный цикл учётных записей, минимальные привилегии, отзыв доступа и аудит действий.

Раздел **«Безопасность данных»** имеет наивысший приоритет. CRM, сервисы продаж и ЖКУ обрабатывают персональные и финансовые данные; по исходной C4-диаграмме сырые CDC-потоки попадают в хранилище, а пользователи уже видели в личном кабинете данные других клиентов. Резервное копирование баз данных снижает риск потери, но отдельно требуется проверить защиту копий, восстановление, классификацию, целостность, качество, минимизацию и анонимизацию данных.

Раздел **«Защита инфраструктуры»** охватывает собственный ЦОД, приватное облако, мощности облачного провайдера и гибридные среды разработки и тестирования. Из известных мер подтверждён firewall для внешнего пользовательского доступа, однако этого недостаточно для оценки сегментации, защиты межсервисного трафика, обнаружения атак, управления уязвимостями и безопасности облачной конфигурации.

Раздел **«Управление инцидентами»** выбран из-за обнаруженных случаев межклиентского раскрытия данных и слабого информационного взаимодействия: один специалист по ИБ не получает сведения обо всех изменениях команд. Следует проверить централизованный мониторинг, оповещение, порядок эскалации, учения и использование результатов инцидентов и аудитов для улучшения защиты.

Раздел **«Специфические аспекты»** нужен из-за мобильного приложения собственников, удалённого доступа, гибридной инфраструктуры, физического ЦОД и функций «Умного дома», влияющих на физический доступ к жилью. Проверка MDM, VPN, контроля устройств, физической защиты оборудования и безопасной утилизации дополняет базовые меры; безопасность устройств и партнёрской платформы «Умного дома» также должна быть включена в последующий аудит интеграции.

| 2 | Настроены ли требования к сложности паролей и их регулярное обновление? | Нет данных — требуется проверка | Проверить политики AD и собственных баз аутентификации приложений. |

| 4 | Реализован ли принцип минимальных привилегий при назначении ролей и прав доступа? | Нет | Партнёрские API позволяют одной УК читать или изменять данные другой УК. |

| 6 | Ведётся ли журналирование всех операций доступа к системам и данным? Кто имеет доступ к журналам? | Нет данных — требуется проверка | Проверить audit-логи CRM, warehouse, API партнёров и права на журналы. |
| 7 | Используются ли механизмы контроля доступа на основе атрибутов для повышения гибкости управления доступом? | Нет данных — требуется проверка | Проверить атрибуты клиента, собственника, УК и ЖК в правилах авторизации. |
| 8 | Используются ли системы аутентификации пользователей для доступа к системам? | Частично | По исходной C4-диаграмме видны AD, auth-service и auth-db; охват всех систем требует проверки. |
| 9 | Созданы ли замкнутые контуры для подсистем, работающих с чувствительными данными? | Нет | По исходной C4-диаграмме сырые CDC-данные идут в warehouse; API партнёров раскрывают ПДн. |
| 10 | Ограничен ли доступ к системам из внешних источников? | Частично | Клиенты и собственники проходят через firewall; ограничения партнёрских API нарушены. |
| 11 | Ведётся ли единый реестр учётных записей? | Нет | По исходной C4-диаграмме видны несколько AD и отдельные auth-db, то есть реестр не единый. |
| 12 | Используются ли средства управления учётными записями на базе единого реестра? | Нет | По исходной C4-диаграмме контуры AD/auth-db раздельны; единого реестра не видно. |
| 13 | Применяются ли средства для отзыва прав доступа? | Нет данных — требуется проверка | Проверить отзыв в AD, локальных auth DB и учётных данных партнёров. |
| 14 | Используются ли средства централизованного контроля доступа? | Частично | По исходной C4-диаграмме AD централизует отдельные контуры; общего контроля не видно. |

## II. Безопасность данных

| № | Вопрос | Статус | Комментарий |
| --- | --- | --- | --- |
| 1 | Разработана ли политика классификации данных, и актуализируется ли она в соответствии с действующим законодательством? | Нет данных — требуется проверка | Проверить политику для ПДн, сделок, платежей, телеметрии и данных «Умного дома». |
| 2 | Используется ли шифрование на уровне базы данных, файловой системы и при передаче данных по сети? | Нет данных — требуется проверка | По исходной C4-диаграмме проверить БД, CDC-транспорт, warehouse и партнёрские API. |
| 3 | Реализованы ли механизмы управления ключами шифрования? | Нет данных — требуется проверка | Проверить KMS/HSM, владельцев ключей, ротацию и разделение сред. |
| 4 | Проводится ли регулярное резервное копирование данных? Хранятся ли резервные копии в защищённых хранилищах? | Частично | Бэкапы всех БД создаются на нужную глубину; защита хранилища не описана. |
| 5 | Выполняется ли регулярное тестирование процесса восстановления данных из резервных копий? | Нет данных — требуется проверка | Запросить протоколы restore-тестов для каждой БД и измеренные RTO/RPO. |
| 6 | Ограничен ли доступ к резервным копиям данных, и зашифрованы ли они? | Нет данных — требуется проверка | Проверить ACL и шифрование backup-хранилищ ЦОД и облачного провайдера. |
| 7 | Ведётся ли учёт персональных данных, и применяются ли специальные процедуры обработки и хранения для различных типов данных? | Нет данных — требуется проверка | Составить реестр ПДн в CRM, онлайн-сделке, ЖКУ, API и warehouse. |
| 8 | Осуществляется ли мониторинг доступа к данным на основе их классификации? Используются ли метки безопасности для маркировки данных? | Нет данных — требуется проверка | По исходной C4-диаграмме проверить метки ПДн в источниках, CDC и warehouse. |
| 9 | Разработаны ли процессы и системы Data Governance для управления данными? | Нет | Точки регистрации и внутренние потоки не координируются и контролируются несистемно. |
| 10 | Реализованы ли системы или процессы безопасного уничтожения данных? | Нет данных — требуется проверка | По исходной C4-диаграмме проверить удаление в БД, бэкапах, CDC и warehouse. |
| 11 | Используются ли системы или процессы контроля целостности данных? | Нет данных — требуется проверка | Чужое Ф. И. О. — сигнал дефекта разграничения/качества; по исходной C4-диаграмме проверить client/tenant ID, CDC integrity и reconciliation. |
| 12 | Реализованы ли системы или процессы контроля сохранности данных? | Частично | Бэкапы всех БД есть; по исходной C4-диаграмме проверить полноту CDC и warehouse. |
| 13 | Применяются ли средства или процессы анонимизации данных? | Нет данных — требуется проверка | Проверить маскирование ПДн в warehouse, BI, ML/AI и тестовых средах. |
| 14 | Разработана ли инструкция по процессу восстановления данных? | Нет данных — требуется проверка | Запросить runbook восстановления БД и зависимых бизнес-сервисов. |

## Приоритетные действия

1. Немедленно устранить межклиентский и межтенантный доступ: ввести tenant isolation и объектную авторизацию в CRM, личном кабинете и API управляющих компаний, затем проверить исправление негативными тестами.
2. По исходной C4-диаграмме инвентаризировать потоки ПДн через CDC до warehouse, ограничить сырые данные, внедрить классификацию, маскирование и аудит.
3. Объединить управление идентификацией: определить целевую IdP/AD-модель, включить MFA для критических систем и формализовать выдачу, пересмотр и отзыв прав.
4. Наладить управление инцидентами и изменениями: назначить ответственных в командах, обеспечить обязательное согласование с ИБ, централизовать логи и алерты, утвердить IR-план.
5. Подтвердить устойчивость инфраструктуры: проверить восстановление из бэкапов, защиту копий, сегментацию гибридной среды, уязвимости и физическую безопасность ЦОД.
