# Проектная работа: аудит безопасности PropDevelopment

## Цель

Подготовить решение семи учебных заданий пятого спринта в публичном репозитории `architecture-pro-propdevelopment`. Результат должен полностью закрывать критерии задания, оставаться понятным ревьюеру и выглядеть как самостоятельная аккуратная работа студента.

## Структура результата

В корне репозитория создаются директории `Task1`–`Task7` и общий `README.md`. В README будет краткая навигация по решениям и оговорка об исходных материалах. Каждый каталог содержит только относящиеся к заданию артефакты и, при необходимости, короткий README с командами проверки.

## Решения по заданиям

### Task1 — классификация данных

Создать редактируемую mind map в формате draw.io. Центральный узел — «Безопасность данных», следующий уровень — публичные, внутренние, конфиденциальные и секретные данные. Для конкретных данных PropDevelopment указать актуальные риски, оценки «незначительный / значительный / критический» и краткие обоснования.

### Task2 — чек-лист бизнес-систем

Взять `IB.md` как исходный шаблон. Сохранить релевантные разделы: управление доступом, безопасность данных, защита инфраструктуры, управление инцидентами и специфические аспекты. Перед таблицей объяснить выбор. Поля заполнять только на основании кейса и диаграммы; отсутствие сведений отмечать как «Нет данных — требуется проверка», не выдавая предположение за факт.

### Task3 — внешние интеграции

Создать контекстную и обновлённую контейнерную C4-диаграммы в draw.io. Мобильное приложение собственника обращается к внутреннему контуру PropDevelopment. Внутренний сервис интеграции с «Умным домом» изолирует партнёрский API, обеспечивает авторизацию, аудит, ограничение запросов и разделение данных управляющих компаний. Биометрия и автомобильные номера обрабатываются по принципам минимизации, целевого использования и явного согласия.

В требованиях описать TLS, OAuth 2.0/OIDC для пользовательского контекста, mTLS и client credentials для межсервисного обмена, краткоживущие токены, scopes, tenant isolation, идемпотентность, таймауты, повторные попытки, журналирование без чувствительных данных, управление секретами и реагирование на сбои.

### Task4 — Kubernetes RBAC

Сформировать роли просмотра, разработчика в выделенном namespace, оператора и ограниченного администратора безопасности. Отдельно ограничить чтение Secrets и изменение RBAC. Подготовить таблицу и три идемпотентных Bash-скрипта: создание пользователей/учётных данных, создание ролей и привязка субъектов. Скрипты должны явно показывать создаваемые ресурсы и не встраивать постоянные закрытые ключи в репозиторий.

### Task5 — NetworkPolicy

Описать четыре Nginx Deployment/Service с метками ролей. Применить default-deny для ingress и egress и разрешить двусторонний трафик только между `front-end` ↔ `back-end-api` и `admin-front-end` ↔ `admin-back-end-api`, включая DNS для исходящих обращений. Манифест хранится одним проверяемым файлом.

### Task6 — аудит Kubernetes

Подготовить `analysis.md`, Bash-скрипт фильтрации JSON Lines и `audit-extract.json`. Скрипт выявляет чтение Secrets, привилегированные поды, `pods/exec`, опасные RoleBinding/ClusterRoleBinding и попытки изменения audit policy. Поскольку исходный `audit.log` отсутствует, пример выжимки создаётся как валидный демонстрационный набор событий по сценарию задания. Это ограничение явно указывается в отчёте; скрипт остаётся пригодным для настоящего лога.

### Task7 — безопасность контейнеров

Создать namespace с PodSecurity `restricted`, три намеренно небезопасных и три исправленных манифеста. Безопасные варианты используют non-root UID, `allowPrivilegeEscalation: false`, drop capabilities, seccomp RuntimeDefault, read-only root filesystem и временные writable volumes там, где они нужны Nginx.

Gatekeeper включает три требуемых ConstraintTemplate: запрет privileged, запрет hostPath и обязательные `runAsNonRoot` вместе с `readOnlyRootFilesystem`. Скрипты проверки демонстрируют отклонение небезопасных и принятие безопасных ресурсов, не считая ожидаемые отклонения ошибкой всего теста.

## Проверка

- XML-файлы draw.io должны быть well-formed.
- Markdown проверяется на заполненность и отсутствие внутренних противоречий.
- JSON проверяется через `jq`.
- Bash-скрипты проходят `bash -n`.
- Kubernetes-манифесты проходят клиентскую или серверную dry-run-проверку в зависимости от доступности CRD и кластера.
- Сетевые политики по возможности проверяются в Minikube с CNI, поддерживающим NetworkPolicy.
- В README фиксируются фактически выполненные команды и ограничения среды.

## Границы и допущения

Исходниками считаются описание задания, `C4-diagram.png`, `PropDevelopment_С4_model.drawio.xml`, `IB.md` и шаблон RBAC из корневой папки. Реальный audit log отсутствует. Публикация репозитория, push и создание pull request выполняются только по отдельному разрешению пользователя.

## Критерии готовности

Все требуемые заданием файлы находятся в `Task1`–`Task7`, открываются и проходят применимые проверки. Репозиторий готов к публикации одним pull request, но внешние действия не выполняются автоматически.
